第4章では、Microsoft 365 Copilotを利用して、これまでの検討結果をExcel仕様書へ変換した。

Excelへ整理したことで、現行仕様、変更後仕様、エラー条件、処理内容、影響範囲、判断理由、試験観点などを一覧できるようになった。

しかし、自分でExcelをレビューしたところ、表の内容には誤りがあることが分かった。

特に、処理の実行順序が実際のコードと異なっていた。

Excel上の誤りを調査する過程で、自分自身の現行仕様に対する理解も改めた。

コードを個別に確認していた段階では把握しきれていなかった処理の前後関係や、複数の関数にまたがる呼出し関係が明らかになった。

ただし、正しい仕様を理解した後、それをMicrosoft 365 Copilotへ一つずつ自然言語で説明し、Excelの各行を修正させる方法では時間がかかる。

処理順序、関数間の呼出し関係、レジストリ読出しのタイミング、復号条件、正常系と異常系の分岐、エラー発生後の停止位置、外部システムとの連携前の確認などを個別に説明すると、説明、修正、再確認を何度も繰り返すことになる。

そこで、自分が理解した現在の仕様を、別のAIが扱いやすい構造へ変換し、その結果をMicrosoft 365 Copilotへ渡してExcelへ反映させる方法を採用した。

![](/assets/imported/zenn/e806d1825a4f8ef7.png)

### GitHub Copilotに現在の仕様を整理させる

最初に、GitHub Copilotへ関連するコードを参照させ、現在の処理構造を整理するためのプロンプトを作成させた。

GitHub Copilotには、処理やモジュール、関数間の呼出し関係、レジストリの保存・読出し箇所、暗号化・復号APIの呼出し位置、正常系と異常系の分岐、エラー発生後の停止位置、外部システムとの連携位置をコードから整理させた。

また、コードから確認できない内容を推測で補完しないよう条件を与えた。

ここでは、GitHub CopilotにExcelを直接修正させるのではなく、コード上の現在の仕様を、次のAIへ正確に伝えるための入力情報として整理させた。

### GPTでPlantUMLへ変換する

次に、GitHub Copilotが作成したプロンプトをGPTへ渡し、現在の仕様をPlantUMLとして表現した。

PlantUMLには、処理の開始条件、関数やモジュール間の呼出し順序、レジストリの保存・読出し、暗号化・復号APIの実行、正常系と異常系の分岐、エラー発生後の停止位置、外部システムとの連携までの流れを表現した。

自然言語だけで現在の仕様を説明する場合と比べ、PlantUMLを用いることで、処理の順序と分岐関係を一つの構造として確認できるようになった。

### 人間が現在の仕様と照合する

GPTが生成したPlantUMLについては、自分が実際のコードと照合した。

コード上の呼出し順序と一致しているか、存在しない処理が追加されていないか、必要な分岐が欠けていないかを確認した。

さらに、レジストリ読出しと復号のタイミング、エラー発生後の停止位置、外部システムとの連携位置、責務範囲についても確認した。

誤りがある箇所は修正し、PlantUMLが現在の仕様を正しく表していることを確認した。

### Microsoft 365 Copilotへ現在の仕様を伝える

確認済みのPlantUMLをMicrosoft 365 Copilotへ渡し、Excel仕様書を修正させた。

これにより、自分がExcelの各行について修正内容を一つずつ説明する代わりに、現在の仕様全体を構造化された情報としてMicrosoft 365 Copilotへ伝えることができた。

Microsoft 365 Copilotには、PlantUMLを基に、処理順序、レジストリ読出しと復号のタイミング、関数間の呼出し関係、正常系と異常系の分岐条件、エラー発生後の停止位置、外部システムとの連携条件などをExcelへ反映させた。

修正後のExcelは再度自分でレビューし、コード、PlantUML、設計方針との整合性を確認した。

> Excelだけでは把握しにくかった動的構造をPlantUMLへ変換し、人間がコードと照合したうえで、その確認済み仕様をMicrosoft 365 Copilotへ渡してExcelへ再反映した。

### AI間で成果物を受け渡す

今回の工程では、自分が理解した内容をMicrosoft 365 Copilotへすべて手作業で説明するのではなく、GitHub CopilotとGPTを経由して現在の仕様を構造化した。

| 担当 | この工程での役割 |
|---|---|
| GitHub Copilot | コードから処理、呼出し関係、分岐、外部連携位置を抽出する |
| GPT | 抽出された情報をPlantUMLとして構造化する |
| 人間 | PlantUMLを実コードと照合し、誤りを修正する |
| Microsoft 365 Copilot | 確認済みPlantUMLを基にExcel仕様書を修正する |
| サブ審議 | 最終仕様を組織として確認・承認する |

この方法により、Excelの誤りを一行ずつ修正するのではなく、正しい仕様全体をAIへ伝えたうえで表へ反映させることができた。

重要なのは、PlantUMLを単なる説明図として作成したことではない。

> 自分が理解した現在の仕様を、Microsoft 365 Copilotへ受け渡すための中間成果物として利用した。

### サブ審議による最終確認

Excelの修正と自分によるレビューを終えた後、最終成果物についてサブ審議を実施した。

サブ審議では、設計方針、実現方法、処理フロー、責務範囲、影響範囲、試験観点を説明した。

その結果、作成した仕様について承認を得た。

これにより、複数AIを利用して作成・修正した成果物を担当者個人の判断だけで完結させず、通常の組織的な審議プロセスを通じて正式な仕様として確定した。

### 本章の位置付け

本章では、Excel仕様書の誤りを起点として現在の仕様を理解し直し、GitHub CopilotとGPTによってPlantUMLへ構造化した。

その確認済みの情報をMicrosoft 365 Copilotへ受け渡してExcelへ反映し、最終的にサブ審議によって正式な仕様として確定した。

> AI間で成果物を受け渡すことで、人間が修正内容を一項目ずつ説明する負担を抑えながら、コード上の現在仕様をExcelへ反映できた。
