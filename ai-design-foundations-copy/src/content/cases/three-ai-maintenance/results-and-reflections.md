## 第7章　成果と考察

今回の取り組みでは、CRA対応に伴うセキュリティ要件の強化を契機として、レガシーシステムの暗号処理と異常系を見直した。

従来の暗号処理をCNG APIおよびDPAPIを利用する方式へ変更したことで、暗号化・復号APIのエラー処理を新たに設計する必要が生じた。

また、暗号化パスワードを保存するレジストリについても異常系が十分に定義されていなかったため、暗号方式の変更だけでなく、レジストリ異常、後続処理への影響、利用者への案内、責務範囲まで含めて完全化保守を行った。

この一連の工程では、GPT、GitHub Copilot、Microsoft 365 Copilotへ同じことをさせるのではなく、それぞれが扱いやすい情報と得意な処理に応じて役割を分けた。

### 完全化保守として得られた成果

今回の変更によって、暗号化・復号APIおよびレジストリに関する未定義の異常系を整理し、異常状態のまま後続処理へ進ませない仕様を確定した。

復号できない値を無理に利用せず、利用者向けの基本的な復旧手段はアンインストールと再インストールへ統一した。

一方、OSやWindowsプロファイルなど、本システムだけでは制御できない問題については、責務範囲外として明確化した。

最終的には、コード上の事実、PlantUMLで確認した動的な処理フロー、Excel仕様書の内容を整合させたうえで、承認済み仕様に基づくコード修正と単体テストまで実施した。

これにより、既存の正常系を大きく変更することなく、新たに必要となった異常系を追加し、セキュリティ要件の強化と保守性の確保を両立できた。

### 外部委託を不要とした

従来、この種の保守開発では、委託先へ実装を依頼していた。

今回は、要件整理、実現方法の具体化、仕様書作成、コード修正、単体テストまでを、複数AIを利用しながら自社内で進めた。

その結果、従来必要だった外部委託を行わずに対応できた。

削減できたのは、実装費だけではない。

| 削減した工程 | 内容 |
|---|---|
| 見積り | 委託先への見積り依頼と内容確認 |
| 調整 | 開発スケジュールや実施内容の調整 |
| 受入れ | 委託先成果物のレビュー |
| 情報伝達 | 実装上の事情や設計意図を委託先へ説明する作業 |

特にレガシーシステムでは、仕様書だけでは表現しきれない実装上の事情や運用条件が存在する。

今回は、設計意図を持つ担当者が、GitHub Copilotによるコード探索から実装、単体テストまで連続して扱った。

そのため、工程を外部へ受け渡す際に生じる説明や認識合わせのコストも抑えることができた。

### 想定開発期間を約7割短縮した

今回の開発では、当初想定していた期間と比較して、開発期間を約7割短縮できた。

この結果は、AIによるコード生成だけで得られたものではない。

要件検討から実装、試験まで、工程全体で時間を短縮した結果である。

主な短縮要因は、次のように整理できる。

| 工程 | AI活用による効果 |
|---|---|
| 要件検討 | GPTとの対話により、前提から制約条件と要件案を早期に整理 |
| 方針決定 | 早い段階で上司レビューを行い、大きな手戻りを抑制 |
| コード調査 | GitHub Copilotを意味検索として利用し、関連箇所を探索 |
| 影響分析 | AIの指摘を人間が再評価し、不要な改修を対象外とした |
| 仕様化 | Microsoft 365 Copilotで検討内容をExcel仕様書へ反映 |
| 動的構造確認 | PlantUMLによって処理順序や分岐を可視化 |
| 実装 | 変更対象を関数単位に限定してコード生成 |
| 試験 | 関数ごとにレビューと単体テストを実施 |
| 委託工程 | 見積り、説明、受入れ、差戻しを削減 |

したがって、約7割という短縮は、

> AIによって実装だけを高速化したのではなく、要件検討、調査、仕様化、実装、試験までの開発工程全体を短縮した成果

と整理できる。

### 3つのAIを役割分担させた

今回の取り組みでは、三つのAIへ同じ質問を投げ、回答を比較したわけではない。

それぞれが接続できる情報と得意な処理に応じて、役割を分けた。

| 担当 | 主な役割 |
|---|---|
| GPT | 前提から制約条件を展開する、要件案や設計上の論点を整理する、PlantUMLを生成する |
| GitHub Copilot | コードを意味から探索する、実現方法を具体化する、コード修正とレビューを支援する |
| Microsoft 365 Copilot | 検討結果を既存のExcel仕様書へ反映する |
| 人間 | 前提と優先順位を定める、AIの出力を検証する、要件・責務範囲・実装方法・品質を判断する |
| 上司 | 方針や最終仕様を組織として確認し、承認する |

GitHub Copilotはコード上の事実に近く、Microsoft 365 CopilotはOffice成果物に近い。

GPTは、人間が与えた前提や判断基準と、コード調査から得た情報を組み合わせ、論点や構造を整理する役割に適していた。

この違いを利用することで、次の工程を一つにつなげた。

![](/assets/imported/zenn/50d50e92bdbef060.png)

重要なのは、AI同士を単純に並べたことではない。

> それぞれのAIが得意とする情報形式へ成果物を変換しながら、次の工程へ受け渡した

ことにある。

### AI出力はリスクに応じて扱う

今回の工程では、AIの出力を一律に疑ったわけでも、一律に正しいものとして採用したわけでもない。

出力がどの工程で利用されるか、誤りが最終成果物へどの程度影響するかによって、人間による確認の強度を変えた。

例えば、GitHub Copilotに作成させたPlantUML生成用のプロンプトは、そのまま次の工程で利用した。

プロンプト自体は最終仕様ではなく、GPTへコード上の処理構造を伝えるための中間成果物である。

仮に表現に不足があっても、生成されたPlantUMLを人間がコードと照合することで、後工程で誤りを検出できる。

一方、最終要件、責務範囲、コード上の事実、生成コード、テスト結果などは、誤りが品質問題へ直接つながるため、人間による検証を必須とした。

今回の扱いは、大きく三段階に分けられる。

| 確認レベル | 例 | 扱い |
|---|---|---|
| 後工程で確認できる中間成果物 | AI間で渡すプロンプト、文章構成案、調査観点 | AI出力を積極的に利用 |
| 設計へ影響する成果物 | PlantUML、Excel仕様書、要件候補、実装案、テスト観点 | 人間が内容を確認して利用 |
| 品質・責任に直結する情報 | コード上の事実、最終要件、責務範囲、生成コード、テスト結果 | 必ず人間が検証 |

この考え方を一言で表すと、

> 後工程で検証できる中間成果物は積極的に利用し、品質や責任に直結する判断は人間が検証する

という原則になる。

すべてのAI出力を人間がゼロから作り直していては、AIを利用する効果が失われる。

一方、重要な設計判断までAIの出力を無条件に採用すれば、品質を保証できない。

確認コストと誤りの影響を見ながら、AIに置く信頼の強度を変えることが重要だった。

### 成果物をAI間の共通言語として利用する

今回の工程では、自然言語、コード、PlantUML、Excelという複数の形式を使い分けた。

| 形式 | 主な用途 |
|---|---|
| 自然言語 | 前提、制約条件、要件案、設計上の論点を検討する |
| コード | 現在の実装上の事実を確認する |
| PlantUML | 処理順序、分岐、呼出し関係などの動的構造を表現する |
| Excel | 要件、判断理由、責務範囲、影響範囲、試験観点を仕様として管理する |

一つの形式だけですべてを表現することはできなかった。

Excelは一覧性に優れる一方、動的な処理構造を表現しにくい。

PlantUMLは処理順序や分岐を表現しやすい一方、判断理由、責務範囲、試験観点を管理する用途には向いていない。

コードは最も実装上の事実に近いが、そのままでは設計判断や要件を把握しにくい。

そこで、コードを参照できるGitHub CopilotからGPTへ情報を渡し、PlantUMLとして現在の仕様を構造化した。

その確認済みPlantUMLをMicrosoft 365 Copilotへ渡すことで、自分がExcelの各行を一つずつ説明することなく、現在の仕様をまとめて反映できた。

> 成果物そのものを、AI間で情報を受け渡すための共通言語として利用した

ことも、今回の工数削減を支えた要因である。

### 今回の方法が成立した条件と限界

今回の方法が成立した大きな理由は、変更範囲が限定されていたことである。

対象は新しいエラー処理の追加であり、既存アーキテクチャや主要な正常系を大きく変更するものではなかった。

そのため、変更対象となる関数を特定し、既存動作を維持しながら異常系だけを追加し、関数単位でレビューと単体テストを行うことができた。

一方、次のような案件では、今回と同じ方法をそのまま適用することは難しい。

- 多数のモジュールを横断する変更
- アーキテクチャそのものの変更
- 正常系の業務フローを大きく変更する開発
- 複数システム間で大規模な要件調整が必要な案件
- コード、仕様書、実際の運用が大きく乖離しているシステム
- AIへ渡せる情報が大きく制限される環境
- 自動復旧や高可用性そのものが主要要件となるシステム

したがって、今回の方法は特に、

> 変更範囲が限定され、既存動作を維持しながら異常系を追加するレガシーシステムの完全化保守

に適している。

### まとめ

今回の取り組みでは、CRA対応による暗号処理の変更をきっかけとして、未定義だった異常系を整理し、レガシーシステムの安全性と保守性を高める完全化保守を行った。

その結果、外部委託を行わず、要件整理から仕様化、コード修正、単体テストまでを内製で実施できた。

また、委託に伴う開発費と調整工数を削減し、当初想定していた開発期間と比較して約7割短縮できた。

この成果は、AIにシステム設計や実装を丸投げしたことで得られたものではない。

> 人間が設計責任を持ったまま、GPT、GitHub Copilot、Microsoft 365 Copilotを一つの保守工程としてオーケストレーションし、それぞれの強みを利用して工程全体を短縮した

ことにある。

AIに何を任せるかだけでなく、どの成果物をどのAIへ渡すか、どこで人間が確認するか、どの判断を人間が保持するかまで含めて設計したことが、今回の取り組みの中心である。
