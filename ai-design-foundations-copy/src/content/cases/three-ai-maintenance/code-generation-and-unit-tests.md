## 第6章　全体像を共有しながら、コード生成と単体テストを進める

第5章で仕様が承認された後、実装と単体テストへ移行した。

今回の変更は、既存機能を全面的に作り直すものではなく、暗号化・復号APIおよびレジストリ異常に対するエラー処理を追加するものである。

変更対象となる関数も限定されていたため、GitHub Copilotへ一度に大量のコードを生成させるのではなく、最初に処理全体の構造を共有し、その後、対象となる関数を一つずつ修正する方法を採用した。

### 最初に処理全体を共有する

実装を始める前に、GitHub Copilotへ関連する処理の全体像を示した。

具体的には、対象となる画面、処理フロー、関数間の関係、仕様書の該当箇所などをスクリーンショットとして提示した。

特に共有したのは、暗号化・復号処理の流れと、レジストリへアクセスするタイミングである。

コードの一部分だけを見せると、その関数内では妥当に見えても、処理全体としては不適切な修正案が生成される可能性がある。

そこで、まず変更の目的と処理全体における位置付けを共有し、その後に個別のコード修正へ進んだ。

ただし、スクリーンショットを提示したことで、GitHub Copilotがシステム全体を完全に理解したとはみなしていない。

画像は、コードだけでは伝わりにくい処理関係や文脈を補う情報として利用した。

### 関数を一つずつ修正する

全体像を共有した後、変更対象となる関数を一つずつGitHub Copilotへ提示し、修正案を生成させた。

一度に複数の関数を変更すると、どの変更がどの要件に対応しているか分かりにくくなる。

また、不要なリファクタリングが含まれたり、不具合が発生した際に原因箇所を特定しにくくなったりするため、人間によるレビュー負荷も大きくなる。

そこで、次のサイクルを関数単位で繰り返した。

![](/assets/imported/zenn/31c01dca387ca115.png)

この進め方により、要件と変更箇所の対応関係を維持しながら、段階的に実装できた。

### 最小変更を原則とする

今回の対象は、長期間運用されてきたレガシーシステムである。

コードを調査すると、今回の変更とは直接関係しない設計上の粗さも見つかった。

しかし、それらまで同時に修正すると変更範囲が広がり、新たな不具合を持ち込む可能性が高くなる。

そのため、今回の実装では、

> 承認済みの仕様を、既存動作への影響を最小限にしながら実現する

ことを原則とした。

具体的には、今回の要件に必要な変更だけを行い、既存の正常系や関数構造を不用意に変更しないようにした。

不要なリファクタリング、理由のない関数名や変数名の変更、新しい依存関係の追加も避け、既存のエラー処理方式に可能な限り合わせた。

また、異常を検出した場合は、不正な状態のまま後続処理へ進ませないことを優先した。

これは、技術的に最も洗練されたコードへ変更することよりも、レガシーシステムの安定性と変更リスクの低減を優先した判断である。

### 生成コードを人間がレビューする

GitHub Copilotが生成したコードは、そのまま採用しなかった。

関数ごとに、承認済み仕様との一致、エラー条件の検出方法、正常系への影響、エラー発生後の停止処理を確認した。

さらに、戻り値や状態変数が既存処理と整合しているか、不要な分岐や例外処理が追加されていないか、他の呼出し元へ影響しないか、既存のコーディング規約に適合しているかも確認した。

GitHub Copilotはコードの修正案を生成する役割を担ったが、

> そのコードを採用するかどうかの判断と、最終的な品質責任は人間が持つ

という前提は変えなかった。

### 単体テストを関数単位で実施する

コードレビュー後は、変更した関数ごとに単体テストを実施した。

今回は新たな異常系を追加する変更であるため、正常系を維持できていることに加え、異常発生時に意図した位置で処理を停止できることを重点的に確認した。

主な確認内容は次のとおりである。

| 試験対象 | 確認内容 |
|---|---|
| 暗号化・復号API成功時 | 従来どおり処理が継続し、正しい値が後続処理へ渡される |
| 暗号化・復号API失敗時 | 不正な結果を利用せず、後続処理へ進まない |
| レジストリ値が存在しない場合 | 異常として検出し、処理を継続しない |
| 既存正常系 | 異常系追加によって従来動作が変化していない |

必要に応じて、GitHub Copilotにはテスト観点やテストコードの候補も生成させた。

ただし、何を正しい結果とするかは、承認済みの仕様と実際のコードを基に人間が決定した。

### 今回の方法が成立した条件

今回の方法が成立した大きな理由は、変更範囲が限定されていたことである。

対象は新しいエラー処理の追加であり、既存システムの主要な正常系やアーキテクチャを変更するものではなかった。

そのため、変更対象となる関数を特定し、関数単位で修正と単体テストを繰り返すことができた。

また、既存動作を維持しながら異常系だけを追加する変更だったため、全体像と個々のコード変更の対応関係も人間が把握できた。

一方、大規模な機能追加やアーキテクチャ変更、複数モジュールをまたぐ広範な改修では、同じ方法をそのまま適用することは難しい。

変更箇所が増えるほど、スクリーンショットや対話だけでAIへ十分な文脈を維持させることが難しくなり、人間側のレビュー負荷も増大する。

したがって、今回の実践からは、

> 全体像を共有したうえで、変更対象となる関数を一つずつAIと修正する方法は、変更範囲が限定された完全化保守に適している

と整理できる。

### 本章の位置付け

本章では、承認済み仕様と処理全体の構造をGitHub Copilotへ共有したうえで、変更対象となる関数を一つずつ最小限に修正した。

その都度、人間によるコードレビューと単体テストを行うことで、AIによるコード生成の速度を利用しながら、既存動作の維持と変更リスクの抑制を両立した。

> AIに大量のコードを一括生成させるのではなく、全体像を共有したうえで変更単位を小さく保ち、人間が各段階で品質を確認することが、今回の実装方針である。
