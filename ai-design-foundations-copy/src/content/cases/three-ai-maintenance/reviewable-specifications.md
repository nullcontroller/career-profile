## 第4章　Microsoft 365 Copilotでレビュー可能な仕様書へ変換する

第3章では、GitHub Copilotと人間によるコード調査を通じて、設計方針を既存コードへ適用する方法を具体化した。

次に必要なのは、その検討結果を会話やコード調査の中だけに残さず、設計全体を一覧して確認できる形へ変換することである。

要件、実現方法、影響範囲、判断理由、試験観点が別々の場所に存在したままでは、個々の内容を理解できても、相互の整合性を確認しにくい。

そこでMicrosoft 365 Copilotを利用し、これまでに整理した内容を既存のExcel仕様書形式へ反映した。

### 分散した設計情報をExcelへ集約する

仕様書を作成する前の段階では、設計に必要な情報が一つの場所にまとまっていたわけではない。

人間が定めた保守上の前提、GPTとの対話で整理した論点、上司レビューで承認された方針、GitHub Copilotによるコード調査、人間が確認した実装上の事実が、それぞれ別の形で存在していた。

主な情報源は次のとおりである。

| 情報源 | 主な内容 |
|---|---|
| 人間が定めた前提 | 発生頻度、改修工数、既存影響、安全性、保守性 |
| GPTとの対話 | 選択肢、制約条件、懸念事項、トレードオフ |
| 上司レビュー | 承認された設計方針 |
| 既存コード | 処理順序、呼出し関係、分岐、戻り値、後続処理 |
| コード調査 | エラー検出位置、停止位置、影響範囲、外部連携位置 |
| 人間の判断 | 採用する実現方法、変更しない範囲、責務範囲 |

これらをMicrosoft 365 Copilotへ与え、既存のExcel仕様書へ整理した。

Excelには、主に次の内容を記載した。

| 分類 | 主な記載内容 |
|---|---|
| 仕様 | 現行仕様、変更後仕様、正常系、異常系 |
| エラー処理 | 発生条件、異常時の処理、後続処理を停止する条件 |
| 利用者対応 | 表示する案内、アンインストール・再インストールによる復旧 |
| 変更内容 | 変更対象、既存機能への影響 |
| 設計判断 | 採用理由、コード調査結果、責務範囲 |
| 試験 | 確認すべき試験観点 |

Microsoft 365 Copilotが仕様そのものを決定したわけではない。

> 人間と各AIによって検討・確認された情報を、一覧可能なレビュー媒体へ変換する

ことが、この工程での役割である。

![](/assets/imported/zenn/75f482ba78c7e207.png)

### Excelを使って設計全体をレビューする

Excel仕様書を作成した目的は、完成した仕様を記録することだけではない。

設計者自身が、要件、実装、影響、判断理由、責務範囲、試験観点を一覧し、それぞれの対応関係を確認することにあった。

Microsoft 365 Copilotが生成したExcelについて、主に次の観点からレビューした。

| 確認観点 | 確認内容 |
|---|---|
| 現行仕様 | 実際のコードと一致しているか |
| 変更後仕様 | 承認済みの設計方針と整合しているか |
| 正常系・異常系 | 両者が混在せず、適切に分離されているか |
| 処理の過不足 | 存在しない処理の追加や、必要な分岐の欠落がないか |
| エラー処理 | エラー条件と、その後の処理が対応しているか |
| 影響範囲 | 変更箇所と既存機能への影響が対応しているか |
| 責務範囲 | 本システムが扱う範囲と責務外の範囲が明確か |
| 試験観点 | 仕様変更と確認すべき試験が対応しているか |

Excelへ一覧化したことで、会話やコード調査だけでは見つけにくかった重複、矛盾、説明不足を確認しやすくなった。

特に今回の設計では、レジストリ異常と暗号化・復号APIエラーを原因としては区別しながら、利用者向けの基本的な復旧手段を共通化している。

そのため、処理内容だけでなく、安全性、改修工数、保守性、責務範囲といった判断理由も合わせて確認した。

### Excelの誤りから現在仕様を理解し直す

レビューを進めると、Microsoft 365 Copilotが作成したExcelには複数の誤りがあることが分かった。

特に問題となったのは、動的な処理構造である。

| 問題となった構造 | 内容 |
|---|---|
| 処理順序 | レジストリ読出しと復号の実行順序 |
| 分岐位置 | 正常系から異常系へ切り替わる位置 |
| 停止位置 | エラー発生後にどこで処理を停止するか |
| 呼出し関係 | 複数の処理や関数がどの順序で呼ばれるか |
| 実行タイミング | 同じ処理が異なるタイミングから呼び出される構造 |
| 外部連携 | 外部システムとの連携前に実施される確認 |

Excelは個々の条件や処理を一覧化することには向いているが、処理が時間の流れに沿ってどのようにつながるかを表現することには向いていない。

そのため、動的な構造が単純化され、実際のコードとは異なる内容として整理されている箇所が生じていた。

さらに、この誤りをコードと照合する過程で、自分自身も現行仕様を一部誤って理解していたことが分かった。

個々の関数を確認しているだけでは把握しきれていなかった前後関係や呼出し構造が、Excelとの比較によって明らかになったのである。

このレビューによって得られた結果は、次のように整理できる。

| レビュー対象 | 得られた結果 |
|---|---|
| AIが生成したExcel | 誤った処理順序や呼出し関係を発見した |
| 現行コード | 実際の動的構造を再確認した |
| 人間の理解 | 誤って認識していた現在仕様を修正した |

つまり、このレビューは、**AIが生成した仕様書を確認する作業であると同時に、人間自身の現在仕様に対する理解を更新する作業**にもなった。

### 一項目ずつ修正する方法をやめる

現在仕様を理解し直した後、その内容をMicrosoft 365 Copilotへ一項目ずつ説明し、Excelを修正することもできる。

しかし、動的な構造を自然言語で個別に説明する方法では、多くのやり取りが必要になる。

特に、次の情報を一項目ずつ伝える必要があった。

| 説明が必要な情報 | 内容 |
|---|---|
| 処理順序 | どの処理が先に実行されるか |
| 呼出し関係 | どの関数からどの関数が呼び出されるか |
| 分岐条件 | どの条件で正常系と異常系が分かれるか |
| 停止範囲 | エラー発生時にどこまで処理を停止するか |
| 実行タイミング | 同じ処理がどのタイミングから利用されるか |
| 外部連携 | 外部システムへ到達するまでの処理の流れ |

これらをExcelの各行へ反映するために、一つずつ説明と確認を繰り返す方法では時間がかかる。

そこで、修正方法を次のように変更した。

| 方法 | 役割 |
|---|---|
| GitHub Copilot | コード上の現在仕様を整理する |
| GPT | 現在仕様をPlantUMLへ構造化する |
| 人間 | PlantUMLを実際のコードと照合する |
| Microsoft 365 Copilot | 確認済みの構造をExcelへ反映する |

> 現在の仕様を別のAIが扱いやすい構造へ変換し、その成果物をMicrosoft 365 Copilotへ渡す

という方法である。

次章では、このAI間の受け渡しによって現在仕様をPlantUMLへ構造化し、確認済みの内容をExcel仕様書へ反映する。
