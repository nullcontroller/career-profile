## 第2章　異常系の構造を整理し、設計方針を確定する

第1章では、暗号方式の変更によって新たに考慮する必要が生じた異常系を整理した。

次に必要なのは、それぞれの異常へ個別に対処することではなく、

> どの異常をどこまでシステムが扱い、どの状態で処理を止めるか

という設計方針を決めることである。

そこでまず、人間側で今回の保守における前提を定めた。

| 観点 | 前提 |
|---|---|
| 発生頻度 | 対象となる異常の発生頻度は低い |
| 改修工数 | 異常系のために過大な工数を掛けない |
| 既存影響 | 正常系への変更を最小限にする |
| 安全性 | 判断できない場合は安全側へ倒す |
| 後続処理 | 正常性を確認できない状態では処理を継続しない |
| 責務 | システムが責任を持てる範囲を明確にする |
| 保守性 | 複雑な復旧処理によって将来の保守性を悪化させない |

この時点では、具体的なエラー処理までは決めていない。

これらの前提をGPTへ与え、設計上の選択肢とトレードオフを整理した。

![](/assets/imported/zenn/2728ea73e309755b.png)

### GPTを利用して設計上の選択肢を比較する

当初は、暗号化・復号APIのエラーやレジストリ異常について、原因ごとに異なる復旧処理を設けることも検討した。

しかし、異常ごとに個別処理を実装すると分岐が増え、設計とコードが複雑になる。

また、発生頻度の低い異常に対して自動復旧を充実させても、その実装や保守に必要な工数が見合うとは限らない。

そこでGPTとの対話では、主に次の観点から選択肢を比較した。

- 安全性
- 改修工数
- 既存動作への影響
- 将来の保守性
- OSや利用環境との責務境界

GPTに設計を決定させるのではなく、人間が定めた前提に対して、

**「この方針を取った場合、どのような利点・欠点・責務が発生するか」**

を整理させた。

この比較から、大きく三つの設計判断を行った。

### 判断1　異常状態では後続処理へ進ませない

最も重視したのは、不正な状態のまま処理を継続させないことである。

特に暗号化パスワードは、外部システムとの連携に利用される。

復号に失敗した値を正常な平文パスワードとして扱えば、後続処理で誤った値が利用される可能性がある。

そのため、

> 復号できない場合は、その値を利用せず処理を停止する

ことを基本方針とした。

これは、自動的に処理を継続することよりも、正常性を確認できない状態で重大な品質問題を起こさないことを優先した判断である。

### 判断2　利用者向けの復旧方法は共通化する

レジストリ値か破損している場合、システム自身が元の正しい値を確実に復元できるとは限らない。

暗号復号化APIのエラーについても、原因は入力データだけではない。

権限、Windowsユーザープロファイル、OS内部の状態など、システム単体では制御できない要因によって発生する可能性がある。

これらの原因ごとに個別の復旧処理を実装すると、異常系だけで設計が複雑になる。

そこで、異常原因は内部では区別しつつ、利用者へ案内する基本的な復旧手段は、

> アンインストールと再インストールによって既知の正常状態へ戻す

方法へ統一した。

これは、不確実な状態を部分的に修復するのではなく、一度関連する状態を削除し、正常な状態を再構築する方針である。

ただし、すべてのレジストリ値を同じ重大度では扱わない。

例えば、UIの表示位置など、失われてもシステムの主要機能に影響しない情報については、暗号化パスワードと同じ理由で処理を停止する必要はない。

保存情報の重要度と後続処理への影響に応じて、異常時の扱いを分けることとした。

### 判断3　システムの責務範囲を限定する

アンインストールと再インストールを行っても問題が解消しない場合、原因がOSやWindowsユーザープロファイルに存在する可能性がある。

しかし、本システムがWindowsそのものを修復することはできない。

そこで、

- 本システムが制御できる範囲
- 本システムが正常状態への復旧を保証できる範囲
- OSや利用環境の管理主体が対応すべき範囲

を切り分けた。

OSやWindowsユーザープロファイルなど、本システム単体では制御できない問題については、責務範囲外として仕様へ明記することとした。

これは対応を放棄したのではなく、

> システムが責任を持てない領域まで無理に自動復旧しない

という設計判断である。

### 設計方針を上司レビューで確定する

GPTとの対話によって選択肢とトレードオフを整理した後、上司へ方針レビューを行った。

レビューでは個々のエラー処理だけではなく、

- なぜ安全側へ倒すのか
- なぜ自動復旧を増やさないのか
- なぜ復旧方法を共通化するのか
- どこまでを本システムの責務とするのか

という判断理由も合わせて説明した。

最終的に、次の方針について承認を得た。

| 設計方針 | 内容 |
|---|---|
| 異常時の基本動作 | 正常性を確認できない場合は後続処理を停止する |
| 復号失敗 | 復号できない値を利用しない |
| 異常原因 | レジストリ異常と暗号API異常は原因として区別する |
| 重要度 | 保存情報の重要度によって異常時の扱いを変える |
| 利用者向け復旧 | アンインストールと再インストールを基本とする |
| 自動復旧 | 発生頻度の低い異常へ過度に複雑な処理を追加しない |
| 責務範囲 | OSやWindowsプロファイルなどは本システムの責務外とする |
| 優先事項 | 自動継続よりも、不正な状態で処理を進めないことを優先する |

GPTの役割は、これらの設計方針を決定することではない。

人間が保守上の前提を定め、GPTによって選択肢やトレードオフを整理し、その結果を基に人間が方針を決定した。

さらに上司レビューを通すことで、個人の判断ではなく、組織として承認された設計方針とした。

> 人間が前提を定め、GPTで選択肢とトレードオフを整理し、人間が判断したうえで上司レビューによって確定する。

これが、本章で行った設計工程である。
