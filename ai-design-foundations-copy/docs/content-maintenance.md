# Content Maintenance Policy

AI Design Foundationsは、公開済み文章を固定された移行成果物としてではなく、現在の判断に使える知識として保守する。

## 正本と履歴

- `src/content/` のMarkdownを公開知識の正本とする。
- 変更理由と差分はGitで管理する。
- 出典はfront matterの `source` に保持し、本文の主語にはしない。
- 過去の構成、移行対応、機械的な追跡情報は `migration/` と `docs/history/` に置く。
- 公開本文では、現在の意味、前提、適用範囲を説明する。

## 知識の層

| 層 | 役割 |
|---|---|
| AI Design / AI数学論 / Practices / Reference | 現在の設計知識、理論、適用方法、参照定義 |
| Case Studies / Articles / Books / Series / Essays | 実務事例と公開物。執筆時点の文脈を保ちつつ、現在の補足を加える |
| migration / docs/history / source metadata / Git history | 出典、移行、変更判断の記録 |

## レビュー時の判断

各ページを次のいずれかに分類する。

- **KEEP**：現行の正本として内容を維持する
- **UPDATE**：局所的な表現、前提、リンク、日付を更新する
- **REWRITE**：URLと出典を保ち、本文を現在の理解で再構成する
- **MERGE**：役割を別ページへ統合し、既存URLは案内として維持する
- **SPLIT**：一つの責務を複数の参照ページへ分ける
- **ARCHIVE**：履歴として保持し、通常導線から外す
- **REMOVE_FROM_PUBLIC**：追跡情報は保持し、公開対象から外す

## 品質基準

内容を更新するときは、次を確認する。

1. 事実、数学的定義、説明モデル、設計仮説を混同していないか
2. 適用条件、責任主体、検証方法、失敗時の扱いが読めるか
3. SourceとTopic、出典と現在の分類を混同していないか
4. Summary、Title、分類、リンクが本文と一致しているか
5. 古い媒体名、章番号、移行時の都合が公開本文の理解を妨げていないか
6. 実務事例の結果や数値を変更・誇張していないか
7. substantiveな変更には `updated_at` を付けたか

## 継続レビュー

- 新しい実務・学習・検証結果を得たときに、関連する設計原則とReferenceを見直す。
- モデルや製品の更新だけを理由に一般原則を変更せず、適用条件と実測結果を確認する。
- Publicationの主張が現在の正本と異なる場合、出典を消さず、現在の補足または正本への導線を加える。
- 構造変更時は、既存URL、検索、全体目次、関連記事、Sitemap、RSSを検証する。

更新の契機は、技術前提の変化、実務経験の追加、重複や誤りの発見、設計思想の変更、分類の改善である。

## Review Cycle

- **新規Content追加時**：関連する正本、Reference、内部リンク、重複を確認する。
- **月次の軽量Review**：直近の更新と未整理の知見を確認し、局所的な修正を行う。
- **四半期の全体監査**：分類、重複、古い前提、孤立Page、Summary、Referenceを横断して確認する。
- **大きな設計思想変更時**：関連するCurrent Knowledge、Practice、Case、Publicationを同時に見直す。

日付は目安であり、公開のためだけに内容を更新しない。実務上の知見または判断が変わったときに、変更理由と影響範囲を記録する。
